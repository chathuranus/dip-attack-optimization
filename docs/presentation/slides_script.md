### Slide 5: The SAT attack (Subramanyan et al., 2015)

**On-slide content**
- Build a **miter**: two copies of the locked circuit, same input X, keys K1 and K2
- Ask a SAT solver: is there X, K1, K2 with C(X,K1) ≠ C(X,K2)?
- That X is a **Distinguishing Input Pattern (DIP)**
- Query the oracle with the DIP → Y; add C(X,K1)=Y and C(X,K2)=Y as constraints
- Repeat until UNSAT; any key still consistent is correct

**Speaker script**
> Here's the key idea. Two copies of the locked circuit share the same input, but each has its own key. We ask the solver to find an input where the two copies disagree. That input is a DIP: proof that at least one of the two keys is wrong. We ask the chip for the true output and add it as a constraint, which rules out every key that would give a different output on that input. When the solver can no longer find any disagreement, every remaining key is equivalent, and we pick one.

**Generation prompt**
> Slide titled "The SAT attack". Left half: a miter diagram. Input bus X fans out to two boxes "Locked C (key K1)" and "Locked C (key K2)". Their outputs go into an XOR/compare block labeled "diff = 1?". Right half: a vertical loop flowchart: (1) "SAT? find X,K1,K2 with diff" → if SAT: (2) "DIP = X" → (3) "Query oracle: Y = O(X)" → (4) "Add C(X,K1)=Y, C(X,K2)=Y" → back to (1). If UNSAT: "Extract key from constraints → verify equivalence". Highlight step (2) in a different color with the label "← our focus".

### Slide 6: The attack as key-space elimination

**On-slide content**
- Each DIP + oracle answer **partitions** the remaining keys
- Keys whose output disagrees with the oracle are eliminated
- Attack length = number of DIPs = number of oracle queries
- A good DIP eliminates many wrong keys; a poor one only a few
- The standard attack takes **whatever DIP the solver happens to return**

**Speaker script**
> Here's a more useful way to picture the attack. Think of the set of all keys still consistent with the oracle. A DIP splits that set into groups by the output each key produces. The oracle tells us which group is correct, and the rest are thrown out. So the attack's length depends entirely on how good each split is. The standard SAT attack doesn't try to choose a good one: it takes the first satisfying assignment the solver finds.

**Generation prompt**
> Slide titled "Every DIP partitions the key space". Show a large rounded rectangle "Feasible keys". Show two side-by-side examples. Left, "Weak DIP": the rectangle split into one huge region (consistent with oracle, kept) and a thin sliver (eliminated, greyed). Right, "Strong DIP": the rectangle split into many regions; only one small region is kept, and the rest are greyed out. Caption: "Fewer remaining keys per query → fewer queries overall".

## Section 2: The problem

### Slide 7: Problem statement

**On-slide content**
- SAT-attack cost ≈ #iterations × (DIP solve time + oracle query time)
- Standard SAT: DIP choice is arbitrary, decided by solver heuristics
- Oracle queries are the **physical** bottleneck: each one is a round trip to real silicon
- Modelled JTAG/USB access: ≈ 2 ms per query, regardless of circuit size
- **Research question:** can a deliberately chosen DIP reduce oracle queries without increasing total attack time?

**Speaker script**
> So the problem we focus on is: does DIP selection matter, and can we exploit it? In simulation, an oracle query is just a function call. On real hardware it isn't. We modelled the off-chip path: PC, USB 2.0, an FT2232H JTAG adapter, then the chip. The USB round trip alone is about 2 ms per query, and that's over 99% of the query time. Shifting the bits takes only microseconds. So query count matters, and it matters more the slower the access path is. But a smarter DIP costs more solver time to find, so the real question is the trade-off.

**Generation prompt**
> Slide titled "Problem: the DIP is chosen arbitrarily". Top: an equation in large type: "Attack cost ≈ N_DIP × (T_solve + T_query)". Under N_DIP write "what we reduce" in green; under T_solve write "what smarter selection costs" in orange. Middle: a small horizontal chain diagram: PC → USB 2.0 → FT2232H JTAG → Chip, annotated "T_query ≈ 2 ms (USB round trip dominates, >99%)". Bottom: the research question in a highlighted callout box.

### Slide 11: Approach 1, sampled-key partitioning (idea)

**On-slide content**
- Goal: choose the DIP that splits the feasible key set most evenly
- Sample K = 32 distinct feasible keys (key_solver: oracle constraints only)
- Generate D = 8 distinct candidate DIPs from the miter
- For each candidate: simulate the locked circuit under all 32 keys → group keys by output
- Score = Shannon entropy of the groups; tie-break on smallest largest group
- Worst case eliminated = K − largest class

**Speaker script**
> The first approach takes the partition picture literally. We can't enumerate all 2^32 keys, so we sample: 32 keys consistent with every oracle answer so far, and 8 candidate DIPs. For each candidate, we simulate the locked netlist under each sampled key. No oracle query is needed, because we know the netlist. We group the keys by the output they produce. A DIP that spreads the keys across many equal-sized groups has high entropy, and it guarantees many eliminations whatever the oracle answers. We pick the highest-entropy DIP and break ties on the worst-case group size.

**Generation prompt**
> Slide titled "Approach 1: sampled-key partitioning". Show a 3-stage pipeline, left to right, in orange tones. Stage 1, "Sample": 32 small key icons drawn from a cloud labeled "feasible keys". Stage 2, "Candidates": 8 DIP icons drawn from the miter. Stage 3, "Score": a matrix with 8 rows (DIPs) and 32 columns (keys), each cell colored by output class. Beside each row, its entropy value. Highlight the row with the most varied colors as "selected DIP". Under the pipeline, the formula H = −Σ (n_c/K) log2(n_c/K).

### Slide 12: Approach 1, implementation and optimization

**On-slide content**
- Temporary blocking clauses with push/pop leave the attack's constraints unchanged
- Bottleneck 1: z3 `substitute` + `simplify` per (DIP, key) took ~75% of scoring time
- Fix: **bit-parallel netlist evaluator**: each Python int bit is one key, so all 32 keys in one pass
- Scoring time: **31.8 s → 0.03 s**
- Bottleneck 2: z3 term churn in sampling. Fix: cached literals + direct C-API `Or` / bool reads (−40–55%)
- Reuse the miter's existing model as the first candidate DIP

**Speaker script**
> The first implementation was unusably slow, and profiling showed why: for every DIP–key pair, we asked z3 to substitute the values and simplify the whole output expression. Most of that time went into z3's Python-side debug assertions. We replaced it with a bit-parallel evaluator, `sat_attack/bitwise_eval.py`. A Python integer holds one bit per sampled key, so a single topological pass over the netlist evaluates all 32 keys at once. That cut scoring from 31.8 seconds to 0.03 seconds. The next bottleneck was creating z3 objects for every blocking clause. Caching literals and calling the C API directly cut DIP generation by roughly half. The evaluator is unit-tested against z3 on every gate type.

**Generation prompt**
> Slide titled "Making partitioning fast". Left: a diagram of bit-parallel evaluation. One gate (AND) with two inputs, each a 32-bit word, where each bit column is labeled "key 0 … key 31", and the output word below. Caption: "one pass = 32 keys". Right: a before/after horizontal bar pair showing "Partition scoring: 31.8 s" vs "0.03 s" on a log scale (placeholder for graph G9). Below: 3 short bullets about push/pop scoping, cached literals and reusing the first model.

### Slide 13: Approach 2, MaxSAT-style Hamming maximization

**On-slide content**
- For each output, d_i = C(X,K1)_i ⊕ C(X,K2)_i; Hamming distance = Σ d_i
- Start from the miter's model, with distance h
- Loop: push; add **AtLeast(d_1…d_m, h+1)**; check; pop
- SAT → better DIP, raise h; UNSAT → h is **proven maximal**
- Optional per-check timeout / cap on extra checks (`--dip-timeout-ms`, `--max-extra-checks`)
- Intuition: more differing outputs → more output bits constrain the keys per query

**Speaker script**
> The second approach uses a cheaper proxy. Instead of estimating the partition, we ask: on how many outputs do the two candidate keys disagree? We take the solver's first DIP, then repeatedly demand at least one more differing output, using a cardinality constraint inside a temporary push/pop scope. When that becomes unsat, we've proven the DIP is optimal for this metric. Why might this help? Every output on which the copies differ is a separate bit of the oracle's answer that constrains the key, so a DIP that exercises more outputs tends to eliminate more wrong keys. The cost is extra solver calls per DIP. We also have optional timeout and cap knobs that bound that cost.

**Generation prompt**
> Slide titled "Approach 2: maximize output Hamming distance". Left: the miter diagram, but with the output comparison drawn as m separate XOR gates d_1 … d_m feeding a counter "Σ d_i". Right: a staircase chart where each step is one solver check, h = 2 → 4 → 7 → 9 → "UNSAT: 9 is optimal" (illustrative values), in green. Bottom: a code box with "solver.push(); solver.add(AtLeast(*output_xors, h + 1)); solver.check(); solver.pop()".

### Slide 22: MaxSAT underperforms on the error-correcting circuits

**On-slide content**
- c499 and c1355 compute the same function: a 32-bit single-error-correcting (SEC) circuit
- MaxSAT vs baseline queries: c499 15.4 vs 12.0 and c1355 19.6 vs 17.0 (32-bit); c1355 50.6 vs 38.0 (64-bit); c499 60.8 vs 37.4 (128-bit)
- Both circuits lose, so it's the **function**, not gate-level structure
- Hypothesis: SEC outputs are XOR parity trees, so outputs flip together; high Hamming distance ≠ independent information
- c1355 is also costly for MaxSAT: 95–494 extra solver checks per attack, and its only non-c2670 timeout (128-bit)
- c432 at 128 bits loses too (150.2 ± 84.2 vs 83.6 ± 36.6): high variance

**Speaker script**
> A single-run result had suggested that c1355 was a one-off. With five seeds, the pattern is clearer: MaxSAT does poorly on *both* c499 and c1355, which are two implementations of the same error-correcting function. So it's the function, not the gate structure. Our hypothesis is that in these circuits outputs are parity functions over overlapping inputs. Many outputs flip together, so a DIP that flips many outputs isn't giving many independent bits of information about the key. This is the main limit of Hamming distance as a proxy.

### Slide 25: Conclusion

**On-slide content**
- DIP selection **matters**: the solver's default DIP differs on only 2–4 outputs
- Maximizing output Hamming distance cuts queries by 23–33% at 32–64-bit keys
- But its exact optimization gets expensive fast: 3.5× slower at 128 bits, with no net query gain there
- Hamming distance is a proxy: it fails on parity-heavy (SEC) circuits
- Sampled-key partitioning is limited by candidate diversity, not by its entropy ceiling
- Query savings pay off only when oracle access costs ≳ 40–400 ms per query

**Speaker script**
> Our conclusions. First, the DIP the standard SAT attack picks by accident is far from the most informative one available. Second, a simple, exactly optimized proxy, output Hamming distance, turns that into a 23 to 33% query reduction at moderate key sizes. Third, that advantage has limits: the optimization gets expensive as keys grow, and the proxy misleads on error-correcting circuits. Fourth, partitioning's problem is not its theory but its candidates. And finally, whether any of this matters in practice depends on how expensive the attacker's access to the chip is.
